# Project profile request

The fill-in profile each open source project is asked to provide, so organizers, mentors, and participants know how to contribute well.

**When:** Send at T-20w, right after the maintainer kickoff. Profiles, including starter issues and contribution pathways, due T-14w. Curate as early as possible; refresh weekly once the series starts.
**Sent by / owner:** Program organizer
**Audience:** The lead maintainer or project contact for each participating project

## Template

```text
Subject: Sustaining Open Source Series: your project profile for [Project]

Hi [Mentor name],

Thank you again for joining the kickoff. To get participants ready, we are asking each project for a short profile. Please fill in what you can in the attached outline by [Profile due date]. Links to existing docs are perfect; there is no need to write anything new if it already exists.

Please include starter issues and other ways to take part (community meetings, channels, triage, docs, reviews) with the profile. Curating early matters: in every run so far, finding the right first contribution has been the biggest bottleneck. We'll ask a named owner on your side to refresh the list weekly during the series.

Thank you,
[Program organizer name]
```

### Project profile: [Project]

**1. Project overview**
- What the project does, in two or three sentences.
- Who uses it (industries, notable downstream projects).
- Languages and skills involved, and which parts are approachable with only Python (or the main user-facing language) versus compiled code, build, or packaging.

**2. Onboarding**
- Contributor guide link.
- Development workflow link.
- Build from source / dev environment link, plus any recommended shortcut (for example a single command that installs dependencies and runs tests).
- Known setup pain points, by operating system, if any.

**3. Series-ready issues**
- Target: about [N] issues (15 or more works well for a large cohort), each sized to finish in about a week.
- How you want to mark them: a series-only label, a private list shared with organizers, or no label. Some projects prefer not to label publicly so issues are not claimed early.
- A mix of levels: first contributions, intermediate, and a few harder problems for experienced engineers.
- A few larger pieces of work a small team (3 to 4 people) could finish in ten weeks, with a lead maintainer for each.
- The mentee journey you prefer, for example "1 to 2 curated issues first, then wider areas after 1 to 2 merged contributions."

**4. Contribution pathways beyond pull requests**
- Community or developer meetings participants are welcome to join (day, time with UTC, link or how to request it).
- Project chat channels and forums, and which one to use for the series.
- Triage: reproducing old bug reports, confirming fixes, adding regression tests.
- Docs: tutorials, examples, guides that need review.
- Reviews: whether participants may review or test others' pull requests.
- Answering user questions.

**5. Reviewer bandwidth**
- Names (or handles) of maintainers available during the series. Ideally 3 to 4 per project, so there's cover when someone is away.
- Honestly, how many pull requests a week can you review? We size the cohort to match.
- Roughly how many hours a week each can give, and which office hours they can join.
- Areas of expertise, so mentors can route questions.
- Gaps you already know about (for example, no reviewer for a particular language).

**6. Retrospective**
- Who from the project can join a short retrospective at the end, so the next cohort goes better.

**7. Wish list**
- Areas where a new contributor could make an outsized difference, especially if they stay involved.
- Work that is close to done and needs finishing.

**8. AI policy**
- Link to your AI or automated contributions policy, or the policy you adopt by reference.
- If you have none, a sentence or two on what you expect (for example, disclosure, no AI-written replies to reviewers).

**9. Communication channel for the series**
- Where participants should talk with you: workspace, channel name, how to join (invite link, personal email required, and so on).
- Who to contact directly if something goes wrong.

**10. Definition of success**
- What would make this a success for your project? (For example: participants have a good experience; at least one person keeps contributing after the series; docs measurably improve.)

**11. Mentor contacts**
For each project mentor:
- Name
- Code hosting handle (for example GitHub)
- Preferred email (and a separate one for calendar invites, if different)
- Focus area or project they will lead

## How to use

- Send the outline as an editable doc so maintainers can link instead of rewrite.
- Accept "we will pick issues closer to the start" as a valid answer. Agree a date for it instead.
- Check that section 4 has real entries. Participants who join meetings and channels are the ones who stay.
- Note any reviewer gaps early and plan mentor coverage around them.
- Store contact details only where organizers need them; do not publish mentor emails.
